# Methodology

## 1. Dataset selection: what was checked and why

The brief asked for one authentic fraud dataset with at least 250 k transactions, plus account, transaction, timestamp, amount, type, label, device, IP and sender→receiver fields. Before choosing, each candidate's schema was inspected through the Hugging Face API, and sample rows were read.

| Candidate | Rows available | Device id | IP | Sender → receiver | Verdict |
|---|---|---|---|---|---|
| **BankShield-2M** (Hugging Face, preferred) | **5,000 free sample**; the 2 M version is paid | No: only `device_type` on transactions; `devices.csv` joins to customer, not transaction | Yes, but **unique per transaction**, so no IP can be shared | No receiver account | **Rejected**: cannot support device/IP linkage or money flow, and the free sample is far below 250 k |
| Indian Financial Fraud (Kaggle) | – | – | – | – | Not used: Kaggle needs authenticated API credentials; a dataset with the same base schema was available openly (below) |
| PaySim derivatives (6.3 M rows) | 6.3 M | No | No | Yes | Rejected: no device or IP |
| fraudshield-10m | 20 M | Fingerprints | Yes | No receiver | Rejected: no money flow, and many pre-computed graph features would hide the logic |
| **Nigerian Financial Transactions & Fraud Detection** (Hugging Face, `electricsheepafrica`) | **5,000,000** (V1) | `device_hash` | `ip_address` (shared) | `sender_account` → `receiver_account` | **Selected** |

**Selected file:** `V1-nigerian-financial-transactions-and-fraud-detection-dataset.csv`. V1 holds the 21 original columns. V2 adds about 24 publisher-engineered features, which were deliberately *not* used, so that every behavioural feature in this project is computed transparently in SQL.

**Authenticity statement.** The dataset card describes it as a *synthetic* fraud-detection dataset engineered for the Nigerian fintech context. It is a genuine, public, independently published dataset (the file is checksum-verified), but its transactions and labels were generated by the publisher, not observed at a bank. Every finding in this repository is therefore a finding *about this dataset*. No relationships, devices, IPs or labels were fabricated or added by this project.

**No synthetic extension was needed.** The data contains real (in-dataset) money-flow relationships: 893,115 accounts both send and receive, giving 105 k two-hop chains within 24 hours. It also contains shared devices and shared IPs. The brief's fallback (a labelled synthetic extension) was therefore not used. The only hand-made rows in the repository are the clearly labelled unit-test fixture `sql/tests/test_fixture.sql`. That fixture is loaded into a separate database (`fraud_test`) and never mixed with the analysis.

## 2. Data preparation (`scripts/01_clean_data.py`, DuckDB)

1. **Checksum.** The SHA-256 of the raw file is verified. The raw file is read as text only and never modified.
2. **Schema assertion.** The 21 expected column names are checked in order.
3. **Profiling.** Nulls, blanks, distinct counts and min/max per column are written to `data/processed/column_profile.csv`.
4. **Validation.** 25 rules are run, each returning a count of offending rows, and written to `data/processed/data_quality_checks.csv`. Hard rules must be zero: duplicate ids, duplicate business keys, id formats, missing accounts, unparseable or out-of-range timestamps, non-numeric or non-positive amounts, unknown types, invalid device ids, invalid IPv4 octets, label vocabulary, label/fraud_type consistency, unmapped merchants and persona consistency. **All passed.** Informational rules record self-transfers (6), source nulls, negative `time_since_last_transaction` (2,051,331) and type/merchant contradictions (104,493).
5. **Standardisation.** The pipeline upper-cases codes and normalises device ids and IP octets. It also casts types, rounds amounts to 2 dp, maps booleans to 0/1, and derives `merchant_group`, `txn_date`, `txn_hour` and `is_self_transfer`.
6. **No rows are dropped.** All 5,000,000 rows reach the database. Questionable source fields are retained with a `src_` prefix but not used.

## 3. Detection engine (`sql/fraud_network.sql`, PostgreSQL)

The engine is 37 idempotent steps in ten sections. Every threshold is read from `engine_parameters` through `fraud.p('name')`.

| Section | Technique |
|---|---|
| A Shared device | Range self-join on `(device_id, txn_ts)` for different senders ≤ 1 h apart; the ordering predicate `(ts, id) > (ts, id)` emits each pair once. A Poisson baseline over the observed id space tests whether sharing exceeds chance. |
| B Shared IP | The same range join at 10 min, forced to an index nested loop. Each IP is classed by distinct accounts; IPs with more than 50 accounts are labelled HIGH_DENSITY_SHARED (carrier-NAT-like) and excluded from ring edges. |
| C Velocity | Window functions over time-based `RANGE` frames (`INTERVAL '10 minutes' PRECEDING`), `LAG`/`LEAD`, running `AVG`. Bursts use **gaps-and-islands** (`SUM(new_episode) OVER …`), so every transaction belongs to exactly one episode and is never double-counted. |
| D Money flow | Hops are built first, then a **recursive CTE** walks them with depth, 24 h window and cycle guards. Only maximal chains are kept (see §4). |
| E Flags & score | 12 explainable flags; score = capped sum of a-priori weights; four tiers. |
| F Association | Fraud rate when flagged vs not flagged, lift, relative risk with a log-method 95% CI, and recall. |
| G Rings | Edges from A, B and D, connected components via recursive reachability, then a label-free network score plus a separate label score. Size-adjusted validation follows. |
| H Investigation | `RANK`, `DENSE_RANK`, `ROW_NUMBER`, `LAG`, `LEAD`, `COUNT/SUM/AVG OVER` in three views, plus a prioritised case queue. |
| I Rule evaluation | Confusion matrices for 13 rule variants and four threshold sweeps. |
| K KPIs | One reconciled KPI table used by README, memo, workbook and dashboard. |

## 4. Recursive CTE design (Section D)

```
flow_hops    : (A->B at t1) followed by (B->C at t2), t1 < t2 <= t1 + 24h, no self-transfers
chain anchor : every hop that is not a round trip (C <> A)            -> 2 transactions
chain step   : join flow_hops on hop.txn_in = chain.last_txn
               WHERE hop_count < 6                                     -- depth guard
                 AND next_ts <= chain.start_ts + 24h                  -- whole chain in 24 h
                 AND next_receiver <> ALL(account_path)               -- cycle prevention
dedupe       : DISTINCT ON (txn_path)                                  -- identical paths
maximal only : drop a chain if another chain's txn_path @> it (GIN)   -- sub-path prevention
```

Termination is guaranteed three ways: by the depth guard, by strictly increasing timestamps, and by the cycle check. Round trips (A→B→A) are not chained but are counted separately in `money_flow_hop_stats`. The fixture test proves the cycle, window and sub-path rules on a known example.

## 5. Ring scoring (Section G)

*Potential fraud ring* = a connected group of ≥ 3 accounts whose score is MEDIUM or above.

| Component | Points | Rationale |
|---|---|---|
| Size 3–4 / 5–9 / ≥10 | 5 / 10 / 15 | Larger coordinated groups matter more |
| Link-type diversity: 2 / 3 types | 15 / 25 | Independent evidence types corroborate each other |
| Any shared-device link | 10 | Strongest single linkage type in industry practice |
| Any shared-IP link (non-high-density) | 5 | Weaker: IP sharing is common |
| Any hop forwarded within 1 h | 10 | Fast pass-through is a mule pattern |
| Suspicious member txns ≥1 / ≥3 | 5 / 10 | Behavioural corroboration |
| **Network score** (above, label-free) | 0–75 | Used for validation |
| Label score: share of members labelled ≥50% / ≥34% / >0 | 25 / 15 / 5 | Existing ground truth |

Tiers: CRITICAL ≥ 60, HIGH 40–59, MEDIUM 25–39, LOW < 25.

**Validation without circularity.** Because the ring score uses labels, its tiers cannot be used to "prove" that rings contain fraud. Instead, `ring_validation` bands groups by the **label-free network score**. It then compares the observed number of fraud-labelled members with the number expected for accounts of the same activity level, Σ P(label | sent_txn_count), and reports observed/expected with a 95% interval. This controls a strong confounder: accounts that transact more are mechanically more likely to carry at least one label, and also more likely to be linked.

## 6. Correlation, association and causation

* **Correlation** measures how two numeric variables move together, for example amount and label.
* **Association** (what this project measures) is any statistical dependence between a flag and the label: lift ≠ 1, or relative risk with a CI excluding 1.
* **Causation** would mean that the behaviour *produces* fraud, or that blocking it would *prevent* fraud. Observational, synthetic data cannot establish this. A flag can be associated with the label because the generator wrote that dependence in (as with `new_device_transaction` here), because of confounding (activity level), or by chance across many tests. Any rule recommended from association needs a controlled pilot (champion/challenger) before it is relied on.

## 7. Rule evaluation

Each rule variant is a boolean expression over every one of the 5,000,000 transactions. TP, FP, FN and TN are counted against `is_fraud`. Precision, recall, false-positive rate, fraud-value capture, share of volume held for review, lift over the base rate, FPs per caught fraud and reviews per day are reported. The proposed rule cannot be evaluated as written because there is no account-creation timestamp. Its proxies use *first observed activity* and are labelled `PROXY`. The USD threshold uses ₦750 per $1, an assumption that is swept from $0 to $10,000.

## 8. Quality assurance

`scripts/06_validate.py` performs six groups of checks:

1. A fixture unit test of the whole engine.
2. An independent DuckDB recomputation of headline counts.
3. Engine invariants.
4. Dashboard reconciliation, including an in-browser self-test in headless Microsoft Edge that drives the real filters.
5. Excel formula checks after recalculation in Microsoft Excel.
6. Repository hygiene.

Results: [`reports/validation_report.md`](reports/validation_report.md).

